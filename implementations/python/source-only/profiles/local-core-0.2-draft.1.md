# Experimental local-core profile 0.2-draft.1

Status: proposed, source-only profile specification. This documents the `context-layer/0.2-draft` local proof’s observable contract and remaining gaps; it does not change the core protocol, select a global signing suite, or claim production suitability. The baseline behavior is the public repository at `0a8d016c822f38e8fc857422e133d0699c42a21f`. Normative words in this document apply only to this named profile. The four original vector files and their original manifest remain byte-for-byte unchanged.

This document specifies observable data and behavior, not implementation source. It was prepared by a specification author allowed to inspect the reference. An independent implementer may use this document and the vectors without inspecting reference code. Record the document hash and its review status in the implementation provenance.

This profile describes baseline behavior, including known nonconforming paths. A passing local transcript alone does not establish CL-Core-Lite conformance. Core and schema requirements remain authoritative; permissive baseline parsing is not a conforming relaxation of those requirements.

## 1. Identifiers, inputs, and scope

Wire objects retain `spec_version: "context-layer/0.2-draft"`. Profile version, envelope version 1, receipt-log version 1, and receipt-anchor version 2 are separate identifiers. The conformance adapter version is separate again. Fixed times and public test seeds in the vectors are synthetic test inputs, never deployment credentials.

The fixture JSON Schemas specify portable object shape. The local profile additionally supplies deterministic policy, bundle, approval, and receipt semantics below. Required local controls must not be inferred from an object's schema validity alone. The local consumer always requires a receipt store, even when a bundle's `receipt_contract.required` is false. The basic proof's in-memory store is a test double and is not evidence of durable replay resistance.

## 2. Canonical values, hashes, and records

Define C(value) as compact JSON with object member names recursively sorted lexicographically by UTF-16 code units; arrays retain their order. Strings use ECMAScript JSON string escaping; numeric values are finite IEEE-754 binary64 and use ECMAScript JSON number serialization (`-0` becomes `0`). No whitespace or trailing newline is present. UTF-8 encodes the result. Non-JSON values and cyclic values are errors. C preserves the reference record format; it is not a license to substitute language-default key ordering or number formatting.

Define D(value) as `sha256:` followed by 64 lowercase hexadecimal characters of SHA-256(C(value)). Define H(bytes) similarly over the exact supplied bytes. Hashes have no extra domain-separation prefix.

To finalize an unsigned record U with ID prefix P, compute D(U), then add `id: P + hex_digest` and `integrity: {"algorithm":"sha-256","digest":D(U)}`. U must omit `id` and `integrity`. Verification removes exactly those two members and recomputes both the digest and ID. Other members, including extension members if present, participate in the digest. Prefixes are `urn:cl:decision:`, `urn:cl:bundle:`, `urn:cl:receipt:`, and `urn:cl:proposal:` for the respective records. Request and policy bindings hash the complete supplied objects, not an unsigned projection.

For signatures, use RFC 8785 JCS UTF-8 bytes. JCS rejects lone Unicode surrogates and nonfinite numbers. C and JCS agree on valid Unicode JSON values within this profile's binary64 domain. Historic C accepts escaped lone surrogates whereas the signature path rejects them; an implementer must not silently change existing record-vector bytes. Duplicate JSON member names are an unresolved parser hardening issue in the baseline: parsers currently use last-member-wins parsing, despite JCS's I-JSON assumptions. Do not describe that behavior as secure interoperability. New inputs should have unique names; a future strict parsing revision needs explicit compatibility review.

## 3. Local policy and approvals

The policy JSON in `policy-cases.json` is the local setup contract. Required array fields are `allowed_subjects`, `allowed_requesters`, `allowed_clients`, `allowed_recipients`, `allowed_purpose_codes`, `allowed_tasks`, `allowed_selectors`, and `allowed_actions`. Entries are nonempty exact strings. Optional `allowed_authentication_methods` constrains the request's declared authentication method. `allowed_onward_disclosure` defaults to `["forbidden"]`; `approval_required_selectors` and `approval_required_actions` default to empty arrays. Ordinary and approval-required sets must be disjoint. `maximum_retention` supplies a mode and positive safe-integer seconds; `decision_ttl_seconds` defaults to 300. `version` is a nonempty string. Default issuer is `{"id":"urn:cl:policy-engine:local"}`.

Selectors are objects containing only `predicate`; task contains exactly a lowercase identifier `kind` and Boolean `user_visible`. Wildcard selectors/actions are forbidden. Purpose codes are the seven core registered codes or the core `x.` namespace syntax; informative purpose text is not authorization. Authentication method cannot be empty, `none`, or `anonymous`. Local policy consumes an already authenticated principal; merely declaring `authenticated_by` is not an authentication protocol.

At fixed clock T, check request type/version, nonempty request and subject IDs, requester, subject, client, authentication-method allowlist when configured, recipient, onward disclosure, purpose, task, request expiry strictly after T, retention mode, nonempty selectors/actions, wildcard prohibition, policy rate-limit/anomaly status, and required receipt preflight. A false `rate_limit_ok` denies; a truthy `anomaly_state` other than `normal` denies. Receipt preflight is available only on successful `{ok:true}`. A request receipt pair must be exactly `{level,required}`, with `none/false`, `decision/true`, or `operation/true`. Policy `require_receipts:true` upgrades `none/false` to `operation/true`.

Partition each requested selector/action into ordinary, approval-gated, or denied. Hard failures take precedence and yield `deny`. Otherwise any gated scope without valid approval yields `needs_approval`. Otherwise an empty selector or action grant yields `deny`. Otherwise withheld selectors/actions, reduced retention, or transforms yield `allow_with_reductions`; all other cases yield `allow`. Denied and needs-approval decisions grant empty arrays and zero retention. Granted scope orders ordinary entries first, then approved gated entries, retaining request order within each group. In `deny`, denied selector/action arrays contain all requested scope in request order. In every other state, denied arrays contain out-of-policy scope followed by gated scope lacking valid approval, retaining request order within each group. Thus in `needs_approval`, ordinary scope is in neither array: all grant arrays are empty, but ordinary scope is pending rather than recorded as policy-denied. The state prevents bundle issuance.

An approval carries `id`, `request_digest`, `policy_digest`, `expires_at`, `granted_selectors` (predicate strings), and `granted_actions` (action strings). This is a host-attested local approval, not a cryptographically portable approval format. When gated scope exists, verify in order:

1. Missing approval: `APPROVAL_REQUIRED` / `not_provided`.
2. Non-string ID or mismatch with D(complete request) / D(complete policy): `APPROVAL_BINDING_INVALID` / `binding_invalid`.
3. Unparseable expiry or expiry at/before T: `APPROVAL_EXPIRED` / `expired`.
4. Approval grants do not contain every gated selector/action: `APPROVAL_SCOPE_INCOMPLETE` / `scope_incomplete`.
5. No host verifier: `APPROVAL_UNVERIFIED` / `verifier_missing`.
6. Host verifier throws or returns anything other than Boolean true: `APPROVAL_UNVERIFIED` / `rejected`.
7. Otherwise: `verified`.

The verifier receives the complete approval plus computed request and policy digests. It must attest to a genuinely authenticated user approval of those values using a deployment-defined trust mechanism. Tests inject an explicit synthetic attestation; they do not implement user authentication. The baseline accepts a string ID without enforcing nonempty or exact approval keys. This weak shape is recorded rather than retroactively claimed to be strict.

If no gated scope exists, approval is ignored and verification is `not_required`. A valid approval for gated scope yields an `approval_binding` with `approval_ref`, `request_digest`, `policy_digest`, and the approval's `expires_at`; otherwise binding is null. This profile chooses request/policy binding, not globally one-time approval consumption. Re-evaluating the same bound request is possible. Core single-use-or-request-binding language does not imply an approval-consumption database here.

Decision `expires_at` is min(request expiry, T + decision TTL, verified approval expiry if any); invalid request expiry yields T. Retention is min(request seconds, policy seconds) for an allowed state and zero otherwise. `created_at` and calculated expiry use UTC ISO timestamps with three fractional digits. Decision includes the complete fields in its schema: request reference/digest; policy version/digest; grant/deny arrays; transforms; instructions; retention; onward disclosure; receipt requirement and preflight; approval verification and binding; expiry; and reasons. `reason_codes` have no duplicates. State reason precedes withheld-selector, withheld-action, retention-reduction reasons, then hard-failure reasons. Vector-specified ordering is normative for the vector transcript.

Transforms come from `policy.transforms[predicate]`, default empty; collect granted selectors' entries, remove duplicates, and sort by UTF-16. At most 64 identifiers are allowed. Supported forms are `redact:<predicate>`, `truncate:<predicate>:<positive integer>`, and `compress:task-facts`. The first removes a claim, the second truncates claim text and string values by UTF-16 code units, and the third collapses whitespace in claim text and trims it. For multiple truncation limits use the minimum. A Unicode split can yield a lone surrogate that fails the later JCS signature step; this is a baseline limitation. Bundle instructions default to an empty unique string list.

## 4. Bundle construction and envelope authentication

Issuance verifies the decision record and its binding to the complete request, permits only allow states, and requires a nonexpired authorization and positive retained seconds. Expiry is min(request expiry, decision expiry, issue time + authorized retention). A required issuance receipt must be preflighted before issuance and durably appended before returning the envelope.

Only claims with granted predicates survive; redacted claims are removed. Every surviving claim needs a nonempty provenance string list, from `provenance_refs` or, if absent, `provenance_handles`. For every raw provenance handle S compute D({"source":S}); replace it with `prov_` + hex and add provenance entry `{kind:"opaque_vault_reference",ref:"urn:cl:provenance:"+hex}`. Output claims contain `claim`, `predicate`, `value`, `confidence` (finite, 0 through 1), and unique sorted opaque `provenance_handles`. Sort complete output claims by C(claim). No surviving claims is `NO_CONTEXT_GRANTED`.

Recipient is the request recipient's principal string. Subject alias is `urn:cl:alias:` plus the hex digest of `{"subject_ref":request.subject_ref,"request_ref":request.id,"recipient":recipient_string}`. Capabilities are unique sorted decision grants. Receipt required operations are sorted unique `bundle.consume` plus capabilities. Default issuer is `{"id":"urn:cl:bundle-issuer:local"}`. Construct the fields defined by the scoped-bundle schema, preserving the request's optional purpose, task, decision/policy references, instructions and retention. `single_use` is true; restrictions set `memory_write:"proposal_only"`, `raw_vault_resolution:"forbidden"`, authorized onward disclosure and `retention_seconds` equal to retention seconds. Set `decision_ref` to the finalized decision’s `id`, `decision_digest` to `decision.integrity.digest` (the unsigned decision content digest, not a hash of the finalized record), `request_digest` to `decision.request_digest`, and `policy_snapshot` to the decision’s complete policy snapshot. Finalize as a canonical bundle record.

The authenticated transport envelope contains exactly `envelope_version:1`, `bundle`, and `authentication`. Authentication contains exactly `algorithm:"Ed25519"`, `kid`, and `sig`. Sign JCS(bundle), including its finalized ID and integrity. No envelope members, detached digest, extra prefix, NUL, or context string are added to the signing preimage. This absence of cryptographic domain separation is an explicit experimental design property, not a recommendation. Use distinct deployment signing keys for different purposes.

`sig` is the 64-byte Ed25519 signature in unpadded base64url (86 characters). `kid` selects a preconfigured trusted issuer public key and is not a network lookup or trust bootstrap. Locally generated IDs are 3–255 characters matching `[A-Za-z0-9][A-Za-z0-9._:/~-]+`. Test private material is a raw 32-byte Ed25519 seed; interoperable public material is the corresponding raw 32-byte public key (or standard SPKI/PEM). PKCS#8 seed wrapping, where required by a library, is DER prefix hex `302e020100300506032b657004220420` followed by the seed. A consumer needs only the trusted public key, never the seed.

Consumer rejection order is: require a string no larger than 2,097,152 UTF-8 bytes; parse JSON; validate exact envelope/authentication keys and inner canonical record plus structural local constraints without expiry enforcement; match trusted `kid`; verify signature; enforce recipient and expiry; check revocation; reject prior consumption; receipt preflight; durably append successful `bundle.consume`; then release a session. Digest mutation fails `RECORD_INTEGRITY_MISMATCH` before signature checking. A correctly rehashed forged bundle or wrong signature fails `BUNDLE_AUTHENTICATION_FAILED`. Malformed or unsupported authentication metadata (including legacy HMAC without opt-in) is `INVALID_BUNDLE_AUTHENTICATION` before signature verification. Malformed envelope shape is `INVALID_AUTHENTICATED_BUNDLE`. Wrong key ID is `UNTRUSTED_BUNDLE_AUTHORITY`; recipient, expiry, and replay errors are `BUNDLE_RECIPIENT_MISMATCH`, `BUNDLE_EXPIRED`, and `BUNDLE_REPLAY`.

Revocation provider Boolean true means `BUNDLE_REVOKED`; false permits proceeding; errors or other values mean `REVOCATION_CHECK_FAILED`. A null provider disables external revocation checking and is not evidence of revocation support. Recheck expiry and revocation on context reads, action execution, and memory proposals. A session may perform more than one permitted action; single-use limits opening the bundle, not total handler invocations.

Legacy HMAC verification is a separate explicit opt-in, not default issuance: authentication `{algorithm:"hmac-sha256",key_id,mac}`; MAC is HMAC-SHA-256 of C(bundle), unpadded base64url, 43 characters. New issuance always uses Ed25519. Never accept legacy format merely because an envelope asks for it.

## 5. Receipts, log bytes, and anchor version 2

A receipt is finalized with the receipt ID prefix. Default issuer is `urn:cl:receipt-writer:local`. `created_at`, default `started_at`, and default `completed_at` are the fixed clock's ISO timestamp; supplied start/end are normalized to UTC milliseconds. Outcome is success, failure, or indeterminate; completion cannot precede start. Optional operation references default to null; missing input/output digest inputs become D(null); absent policy digest becomes null. `payload_included` is false, metadata defaults to an empty object, and summary is a required string. `supersedes_ref` is absent unless supplied. The schema controls the exact receipt members and restricted metadata. Raw-vault references and secret-bearing fields are rejected recursively. A receipt is evidence of the writer's assertion, not proof an untrusted external service actually performed an operation.

A receipt log is UTF-8 JSON Lines. Each entry is C(entry) followed by one LF, no BOM. Entry has `log_version:1`, one-based `sequence`, `previous_entry_digest`, `receipt`, and `entry_digest`. Compute `entry_digest` as D(the other four members). Genesis previous digest is `sha256:` plus 64 zeroes. Empty/missing log state has zero entries, zero byte length, zero genesis tail digest, and H(empty bytes). A nonempty log must end in LF; validate every receipt, sequence, previous digest, and entry digest. A semantic entry extension is included in its hash in the baseline reader; output writers emit only the five stated keys.

A separate anchor is UTF-8 JSON Lines, C(record) plus LF. Anchor records have exactly: `anchor_version:2`, `log_id`, zero-based `anchor_sequence`, `entries`, `tail_digest`, `byte_length`, `file_digest`, `previous_sig`, `sig`. `log_id` is D({"receipt_log_path":absolute_native_resolved_log_path}). It intentionally binds a local absolute path and is not a path-independent portable ledger identity. For cross-platform conformance transcripts, explicitly provide the logical resolved path string; do not guess another platform's path normalization.

`tail_digest` is the last log entry digest or genesis digest. `byte_length` counts the exact complete log UTF-8 bytes including LFs. `file_digest` is H(those bytes). `sig` is `ed25519:` plus the unpadded base64url Ed25519 signature of JCS(all anchor members except `sig`), with no additional domain prefix. The externally configured anchor key identifies the signer; the record has no key ID. It must be distinct from other key purposes in production. Genesis anchor has sequence/entries/bytes all zero, H(empty) file digest, genesis tail, and `previous_sig` equal to `ed25519:` plus 86 ASCII zeroes (a sentinel, not a valid signature). Each next record increments sequence and entries by one and binds `previous_sig` to the preceding record's `sig`. Anchor version cannot change within a chain.

New empty storage may create and fsync a signed genesis anchor under the exclusive log lock. A missing anchor must never bootstrap a nonempty log. Existing empty anchor is corruption, not new storage. Compare verified log state with authenticated anchor tail: fewer log entries means `RECEIPT_LOG_ROLLBACK`; more means `RECEIPT_LOG_UNANCHORED_SUFFIX`; equal count with differing bytes, file digest, or tail means `RECEIPT_LOG_REWRITE`. Missing anchor is `RECEIPT_ANCHOR_MISSING`; omitted anchor configuration is `RECEIPT_ANCHOR_REQUIRED`.

Append under one shared interprocess lock across the full read/verify, replay check, log append+fsync, log reread, and anchor append+fsync transaction. Successful consumption is unique by `(receipt.actor, receipt.bundle_ref)` among successful `bundle.consume` receipts. A duplicate append is `RECEIPT_REPLAY_CONFLICT`, mapped by the consumer to `BUNDLE_REPLAY`. Replay state must be rebuilt on consumer restart and enforced transactionally by shared receipt storage for multiple consumers. A process-local set alone is insufficient.

The reference filesystem lock uses exclusive creation at log path plus `.lock`, ownership-token comparison on release, 5,000 ms timeout and 10 ms retry defaults. It never automatically deletes another writer's stale lock. A conforming alternative may use an equivalent cross-process transaction/lock while preserving safety. Crashes between log and anchor append leave an unanchored suffix and fail closed; no automatic recovery is promised. Returning a successful side effect whose completion receipt fails is `INDETERMINATE_OUTCOME`, not safe-to-retry success or failure.

Anchor version 1 is a migration input only: replace `previous_sig/sig` with `previous_mac/mac`; use `hmac-sha256:` plus lowercase hex of HMAC-SHA-256 over UTF-8 `context-layer/receipt-anchor/v1` + one NUL + C(unsigned anchor). Genesis previous MAC is prefix plus 64 zeroes. Verify the entire old anchor and current log with the original key before atomically replacing it with a version 2 chain. Never use unauthenticated migration or accept mixed-version chains. The current default uses a supplied 32-byte seed also as the legacy HMAC key if a separate migration key is absent; this compatibility behavior is not a key-separation recommendation.

Rollback protection is conditional: a protected latest anchor detects modification of only the log. An attacker replacing both files with an older authentic pair defeats it. An external monotonic checkpoint and key custody are outside this profile.

## 6. Memory proposals and synthetic vector setup

After a valid session opens, `memory.propose` permits a pending proposal, never a direct write. Inputs are operation (`add`, `add_or_contradict`, or `retract`), nonempty proposed claims, provenance handles, and rationale. Resolve each handle only through the bundle's opaque provenance map. Finalize a proposal with issuer and submitted-by equal to recipient, subject alias, bundle reference, `pending_validation` status, bundle expiry, and `approval_requirement:["source_required","user_confirm"]` when no provenance is supplied or `["user_confirm"]` otherwise. Unknown handles and raw-vault/direct-write members fail. The exported consumer/session surface exposes no commit-memory or vault-resolution operation.

Original vector transcript setup:

- Apply each request patch as a shallow top-level replacement over a deep JSON copy of the base request. Do not deep-merge nested members.
- All clocks use each file's `fixed_time`. Policy state cases have no receipt store because receipts are not required.
- Approval cases add D(patched request) and D(base policy) to the candidate. `no_verifier` has no attestation; `authenticated` supplies a synthetic verifier attesting that candidate ID and both digests; `expired` overrides expiry with `expired_candidate_expires_at`. No real user approval is implied.
- Exchange cases use the full exchange request/policy/claims, a test receipt store returning `{ok:true}`, the declared public Ed25519 seed and key ID, default bundle issuer, and fixed clock. Record issuer receipts in the test store. Consumer principal is the request's recipient.
- Tampered-value case changes the first context value without rehashing. Capability forgery adds `email.send` to capabilities and required receipt operations, sorts both, and refinalizes the inner bundle while retaining its old signature. Signature forgery sets sig to 86 `A` characters. Raw-material case adds `raw_vault_object:{ref:"vault://synthetic-test-only/objects/forbidden"}` to the unsigned bundle then refinalizes it.
- Receipt rollback case creates two receipts with operations from the vector, actor `urn:agent:synthetic-receipt-vector`, subject `urn:cl:alias:synthetic-receipt-vector`, success outcome, summary `Synthetic test-only receipt vector.`, fixed clock, and defaults above. Append both with the public anchor seed. Retain only the first log line while keeping the newest anchor, then reopen. Expect the specified rollback error. No real or workstation-specific path belongs in committed vectors.
- Memory proposal case opens the exchange envelope, uses the memory-vector candidate fields, and checks pending status, approval requirements, and absent privileged consumer members. Add the named direct-write field to a refinalized unsigned proposal for the negative case.

## 7. Known limitations and unresolved differences

This profile documents, rather than silently repairs, last-member-wins JSON parsing, permissive date parsing on some bundle/policy paths, strict date parsing on receipts, path-bound log identity, absent Ed25519 domain separation, no portable cryptographic approval artifact, and no coordinated log/anchor rollback defense. Schema rejection of unknown bundle fields is stricter than some local runtime validation paths. Implementers must report which layer they tested and must not claim that passing local semantic vectors proves schema-complete validation. These differences need separately reviewed hardening revisions.

A passing kit reports tested scope/version and individual failures. It is not certification, external cryptographic review, or evidence of independent adoption. Original corpus count is four vector sets; six contract fixtures are a separate corpus.
